## 2. 棚卸しで判明した最重要事実

### 2.1 死にモジュール2件 = 1,418B(検討不要レベルの即効案)

mapのImports listを精査した結果、**`ima_adpcm.o`(1,090B)と `pcm_stream.o`(328B)はROM内から1件も参照されていない**:

- `_ima_adpcm_*` / `_pcm_stream_*` のインポータはmap上ゼロ。参照しているのは `tests/` のホストテストのみ
- 実際の音声再生は `src/title_voice_stream.s` の独自Timer3/ch.Dドライバが全て担当している
- 両者がリンクされ続けている理由は `Makefile:21` の `COMMON_ROM_OBJECTS` に明示列挙されているだけ
- `pcm_stream.o` は `.interruptor pcm_stream_irq` によりIRQハンドラだけがcondes経由で生存 = **毎IRQで死んだドライバが走っている**(除外はRAMだけでなく僅かに性能にもプラス)

### 2.2 「タイトルを別メモリに」の実現手段は既にプロジェクト内にある

Lynxに RAM のバンク切り替えは存在しない(ワーキングRAMは64KB固定)。しかし**カートは256KBまでシリアルアクセスでき、現ROMは約197KB空いている**。そして本プロジェクトは既に `open("1")`/`read()`(cc65のlynx-cartビットバンギング読み出し)で音声をカートからストリームしている。**ディレクトリエントリを追加し、シーン遷移時に必要データをRAMの共用バッファへロードし直す「時分割オーバーレイ」は、新規機構ゼロで実装可能**。制約は「読み出しがブロッキング&シーケンシャル」だが、シーン遷移時の数百B〜2KBのロードなら知覚不能。

### 2.3 文字の使用実態(全ソース走査の結果)

- 39グリフ中、全経路で未使用: `1 2 4 8 9 H J K Q U Y Z`(12字)
- ただし数字5字はたまたま `GAME_VERSION_STRING="0.53.7"` に含まれないだけ。**version bumpのたびに必要な数字が変わるため0-9は全部残すのが安全** → 安全に削れるのは英字 `H J K Q U Y Z` の7字 = **49Bのみ**
- フォントは実は**2系統ある**: 5×7(273B+コード989B)とHUD専用3×5(90B+コード944B)。削減余地はグリフ削除よりこの**二重投資の統合**の方が大きい

## 4. 各案の設計詳細

### T0: 死にモジュール除外(合計 ~1,570B)

- `Makefile:21` `COMMON_ROM_OBJECTS` から `ima_adpcm.o` / `pcm_stream.o` を外す。ホストテスト(`tests/test_ima_adpcm.c` 等)は独立ビルドなので影響なし
- 検収: (a) map で両モジュール消滅+Imports listに `_ima_adpcm_*`/`_pcm_stream_*` が居ないこと、(b) タイトル音声・GAME OVER音声の再生確認(実再生は `title_voice_stream.s` なので影響しないはずだが、interruptorテーブルの変化があるため耳で確認)、(c) `make verify` 全PASS
- 診断アセット(T0-3)は `src/static_layer_diagnostic_data.c`(RODATA 64B)と `static_layer.c:409` の `"A V 0 5 6"` 表示、`_title_text_data` 周辺の診断分岐を削除。**APS-053の診断用途が完了しているかユーザーに確認してから**

### T1: フォント統合(1系統化、~580B)

現状の二重投資:

| 系統 | データ | コード | 合計 |
|---|---:|---:|---:|
| 5×7(タイトル/オーバーレイ) | 273 | 989(`build_text_line` 401+`text_font_index` 118+ほか) | 1,262 |
| 3×5(HUD専用) | 90 | 944(`append_hud` 506+`build_hud` 329+`glyph_index` 109) | 1,034 |

- 3×5系を全廃し、HUDも5×7の `build_text_line` 経路で描く。回収: `glyph_bits` 90+`glyph_index` 109+`build_hud` 329 ≒ **528B**(`append_hud` の改修差分でさらに増減)
- HUD文字列は約21文字。5×7では 21×6=126px で画面幅160px内に収まる(現3×5は84px)。**HUD行の高さが5px→7pxに増える**ため、プレイフィールドとの重なりをレイアウト確認する
- pixel照合の期待値は再生成が必要(スクリプトは既存の `generate-static-layer.py` 系で対応可能)
- 同時に未使用英字7字(`H J K Q U Y Z`)を `font_glyphs` から落とし、`text_font_index` を「グリフ存在表参照」に変える(T1-2、▲49B)。**数字0-9と記号3種は全部残す**(version文字列が変わるたびに必要数字が変わるため)
- 発展形(任意): `text_font_index` のif連鎖118Bはテーブル化で数十B縮む可能性があるが、費用対効果が小さいのでdev判断に委ねる

### T2: シーン別カートオーバーレイ(「大胆案」の本命、~1,360B)

**原理**: MAIN常駐のRODATAのうち「シーンごとに排他的にしか使わないデータ」を、カート側の追加ディレクトリエントリへ移し、シーン遷移時に共用バッファ(BSS)へ `open("N")`+`read()` でロードする。RAM節約額 = (排他データ合計) − (最大メンバのバッファサイズ) − ローダコード。

排他グループの実測:

| グループ | 使用シーン | サイズ |
|---|---|---:|
| SKY背景(planet 97+mountain 189+cloud 270+205) | ステージ1のみ | 761 |
| CAVE背景(wall 264+rock 340+near 299) | ステージ2のみ | 903 |
| SPACE背景(star 8+座標34) | ステージ3のみ | 42 |
| タイトルliteral 6種+全角サフィックス | タイトルのみ | 363 |
| **常駐時の合計** | | **2,069** |

- 共用バッファを **max(903) = 928B**(アライン余裕込み)でBSSに1本確保 → 常駐2,069B − バッファ928B − ローダ/シーク表コード(見積150〜250B、係数2適用済み) ≒ **▲900〜1,000B**
- ロードタイミング: タイトル表示開始時(タイトルliteral)、ステージ開始時(該当ステージ背景)。いずれもフェード/イントロ中でブロッキング読み出し(1KB未満)は知覚不能
- 実装機構は**既存流用**: `cfg/lynx-voice.cfg` の `DIRECTORY`(現3エントリ)へエントリ追加+新規セグメント(`file=%O`)を定義し、`src/cart_directory.s` に開始ブロック/オフセットを追記。読み出しは `title_voice.c` と同じ `open("N")`/`read()`。カート空きは約197KBなので容量は無制限扱いでよい
- **注意点**:
  1. `read()` はカート全体で単一カーソル(fdを無視)。**音声ストリーム再生中にオーバーレイロードを走らせるとカーソルが壊れる**。「voice再生中はロード禁止」の排他契約が必要(scratch流用と同型の契約。voice pumpがブロッキングである現構造なら自然に守られるが、アサートを置く)
  2. SCBの `data` ポインタが指す先が固定アドレスのRODATAからBSSバッファに変わる。バッファ内レイアウト(各レイヤのオフセット)は生成スクリプトがヘッダとして吐く
  3. pixel照合ハーネス側もロードを再現する必要がある(照合の期待値生成に組み込む)
- **段階的に薄く始められる**のもこの案の利点: まずタイトルliteralだけ(T2-2、▲360B・バッファはタイトル中に空くscratch領域を検討可)→効果と安定性を確認→背景3グループへ拡張(T2-1)

### T3: 保留カード(発動条件をユーザー判断に固定)

- **T3-1 ADPCMテーブルのオーバーレイ化(▲~1,300B)**: `title_voice_stream.o` のRODATA 2,157B(デルタ/ゲインテーブル)は音声再生中しか使われず、再生はタイトル/GAME OVER限定なので理論上はT2の共用バッファに載せられる(バッファを2.2KBへ拡張、節約=2,157−拡張分1,270 ≒ 900B弱+背景分)。ただし**Timer3 IRQ内から参照されるテーブルのアドレスが可変になる**ため、間接参照化のサイクル増とIRQ安全性の検証が重い。T0〜T2で足りる見込みが高いため保留
- **T3-2 C stack縮小**: v2 §6の序列と条件(high-water再計測+ユーザー承認)を維持。他の全案が尽きた場合のみ

### 検討して不採用にした案(再提起防止)

| 案 | 不採用理由 |
|---|---|
| フォントのRLE/ランレングス圧縮 | フォント本体は273Bしかなく、圧縮しても▲100B前後。展開コードがcc65では数百B(係数2)かかり**収支が逆転する** |
| 文字ごとの可変ビット幅フォント | 節約対象が273Bでは効果が薄く、`build_text_line`(401B)の複雑化でコード増。画面上の字詰め改善が目的なら意味があるが、RAM対策としては不成立 |
| テキスト装飾の簡略化 | 現描画は既に1bpp LITERALで装飾を持っておらず、削るものがない |
| 数字グリフの削減(未使用の`1 2 4 8 9`) | version bumpで必要数字が変わるたびにROMが壊れる時限爆弾になる |
| GAMEVOICE/TITLEVOICEの圧縮・削減 | VOICE領域はRAM外(v2 §1誤り4)。RAM収支に一切効かない |
| RAMバンク切り替え | Lynxのハードにその機構が存在しない。「別メモリ」はカート(=T2オーバーレイ)でのみ実現可能 |

- ゲートが赤字ならT2発動(設計は本書§4で完了済み、実装判断だけで着手可能)
