# APS-028 実施記録(音程レジスタのLFSR周期未補正を修正)

- 課題ID: APS-028
- 版番号: v001
- 実施日: 2026-08-08
- 実施者: Fable5(サブエージェント、model: claude-fable-5、worktree: atari-lynx-shooter-aps028-mikey-study、branch: feature/aps-028-mikey-study)。ISSUES.md/本ブリーフの追記・検収・コミットはRyokoが行った。

## 経緯

APS-024(きらきら星差し替え)以降、APS-026(integrate+envelope)・APS-027(DC平衡LFSRタップ再選定)と2回対策しても「常時鳴り続けるブー音」が解消しなかった。ユーザーから「ネットにあるLynxのサウンドデモROMをリバースエンジニアリングして調査してほしい」との指示を受け、著作権に配慮しOSSのチップチューントラッカーFurnace(tildearrow/furnace)のMIKEY実装(`src/engine/platform/lynx.cpp`)をソースコードレベルの一次資料として調査した。

## 発見(確定的な根本原因)

MIKEYの1チャンネルは、タイマーunderflow1回につき1エッジを出力するのではなく、LFSRを1ビット進めるだけである。可聴波形はLFSRが1周期を完了して初めて繰り返すため、体感周波数は`f_underflow / LFSR周期長`になる(TONE/NOISE=6、METALLIC=63、PULSE=8)。

APS-013由来の`sound_pitch_registers`テーブルは、この周期長で割る補正を一度も行っていなかった。結果、全チャンネルの音程は意図の3〜31倍低い周波数(62〜220Hz帯)で鳴っていた。これがAPS-020以降ずっと聞こえていた「低い唸り・ブー音」の正体である。

APS-026(integrateモード)・APS-027(DC平衡タップ選定)は、レジスタが「意図通りに設定されているか」というレベルでは正しく検証できていたが、その「意図」自体(音程計算式)が誤っていたため、機械的なレジスタ検証では捕捉できなかった。

加えて、旧テーブルは音階も均一な約1.075倍刻みで、mml2cのnote id(1〜16、`(octave-1)*7+degree`でハ長調の音階度数を符号化)が期待する平均律ハ長調とズレていたため、旋律の音程間隔も圧縮されていた。

## 実装

- `sound_pitch_registers`を波形ごと(TONE/METALLIC/NOISE/PULSE)× 16音の2次元テーブルへ拡張。各波形のLFSR周期長で正しく割った上でreload/prescalerを再計算(note id 1=C4〜16=D6、A4=440Hzの平均律ハ長調)。
  - TONE/NOISE(周期6): 最大誤差0.21%
  - METALLIC(周期63): 最大誤差3.60%
  - PULSE(周期8): 最大誤差0.39%
- 生成スクリプト`scripts/gen-pitch-tables.py`を新規追加。テーブル冒頭に「このスクリプトで再生成すること、手書き禁止」を明記。
- `sound_backend_apply()`の参照を`sound_pitch_registers[note-1]`から`sound_pitch_registers[wave][note-1]`へ変更(波形ごとに周期長が異なるため)。
- `include/version.h`を`0.28.0`へ更新。

## 検証(Ryoko独立実施)

- `make clean && ./scripts/verify.sh`: ゲーム524件・サウンド279件PASS、cc65 `-W error`ビルド・LNX検査成功。
- ROM: `dist/asteroid-patrol.lnx` 38,328 bytes、SHA-256 `1b4bba04956b6e5cf4de9b0cd550a3e6b92fe42b36746013d5e6408f70548a11`。
- 手計算による検算(TONE note1=C4): reload=0x9e(158)、prescaler=2。period=(158+1)×2^2=636µs → underflow周波数1572.3Hz → LFSR周期6で除算 → 262.05Hz(C4理論値261.63Hzとの誤差0.16%、Fableの申告値0.21%以内と整合)。

## 過去3回との違い

APS-026/027はレジスタレベルの副次的な問題(integrateモードの誤用、DCバイアス)には正しく対処していたが、その手前にあった音程計算式そのものの誤りには気づけなかった(機械的なレジスタ検証は「設定意図通りか」しか確認できず、「意図自体が正しいか」は検証範囲外だったため)。今回はFurnaceという実際に動作実績のある独立実装の周波数計算式と突き合わせたことで、この構造的な誤りを発見できた。
