## 調査済み原因と修正方針

1. APS-046は通常敵とbossを同じ1体で数え、`game_active_combatant_count()` と `game_combatant_injection_is_valid()` が `normal + boss <= 8` だった。正しくは通常敵=1、活動boss=4。全contractを `normal + boss_count * 4 <= 8` にする。bossは0/1のみなので、boss+4 normalを許可、boss+5 normalと8 normal+bossを拒否する。
2. `src/main.c` は `draw_game()` による `tgi_updatedisplay()` の後で `GAME_FRAME_END_WAIT(tgi_busy())` を行う。これは少数敵の余剰をゲーム全体停止へ吸収する設計であり、実プレイの遅延報告と矛盾する。製品ループからこの意図的なframe-end busy-wait/容量補償を撤去する。75Hz同期はTGIの表示requestと次frame開始時の必要最小限のdisplay-completion同期に戻すか、Lynx SDKの正規同期だけを使う。input→4 logic update→sound→drawの各draw frame cadenceを敵数から独立にし、敵数別にlogic・移動・弾速を遅くしない。CPU較正loop、任意のdelay、動的確保は禁止。
3. APS-045 runtime player gridは現在 `12x10` 内に横一様な `999/77777/888.../888888888888` 帯を持ち、A案プレビューの機首・canopy・delta主翼・keel・engineという識別部位を反映していない。`build/gen/sprite_data.c` はこのJSONを正しく生成し、rendererは `GAME_SPRITE_PLAYER=0`、通常敵はtype→`game_enemy_sprite_ids[9]`、bossはappearance→`game_boss_sprite_ids[4]` を正しく参照するため、根因は描画経路ではなくruntime正本gridのデザイン不整合。A案playerとenemy 9種/boss 3種を、各既存visual canvas・2 frame・palette/run/RODATA制約内で再authoringする。プレビューは概念・部位・配色の正本であり、PNGをROMへ貼り込まない。

## 実装要件

### A. 重み付き容量

- 公開定数を明示: normal weight=1、boss weight=4、limit=8。activityはnormal `active && x < GAME_SCREEN_WIDTH`、boss `active`。player、弾、環境、画面外pre-spawnを含めない。
- Stage JSON/generatorでroot limit=8、boss coexist条件を重み付きで検証する。既存Stageの通常4枠とboss演出を保つ。stage validator/negative mutationで、4 normal+boss受理、5 normal+boss拒否、8 normal受理、8 normal+boss拒否、limit 9拒否を必須化する。
- hostとGearlynx注入/readbackのcountはweighted valueとnormal/boss内訳を記録する。

### B. cadence

- 75HzはTGIのhardware presentationだけを同期源とする。ゲームのdraw frameごとに入力1回、logic 4回、sound 1回、draw/display request 1回を維持し、0/4/8 normalおよび4 normal+boss（weighted 8）の全fixtureで同一回数を契約化する。
- `GAME_FRAME_END_WAIT` とframe-end markerを削除または実際の非遅延同期へ置換し、少数敵の余剰をbusy-waitで使わない。frame startで前displayのcompletionを待つ場合も、次の入力/logicを不必要に止めず、正確な順序・存在意義・単位・閾値をdesign/ISSUESに記録する。
- Gearlynx実ROM verifierは、各fixtureで75 draw frame中にinput poll、4 logic update、sound tick、display request/同期pointを直接観測し、player position delta、player bullet X delta、normal enemy X delta、boss X/script deltaを同じlogic cadenceで確認する。MCP wall-clockは参考値扱いに留め、hardwareイベント/カウンタを合否正本にする。GUI実行も必須。

### C. runtime sprite実証

- type→sprite mapping、boss appearance→sprite mapping、ROM run table、`draw_sprite()`の全経路をhost testで固定し、JSON canonical sprite dataと生成C tableと最終ROM由来の値を照合する。old stripe player mutationとmapping mutationをnegativeとして拒否する。
- player A案は12x10の範囲で、1px nose、canopy、非連続/テーパーしたdelta主翼、keel/notch、engine flareをrole別セルで読めるようにする。横一様の長い帯・輪郭だけ・単一図形は禁止。通常敵9種/boss3種もAPS-044の固有部位を維持する。
- Gearlynx証跡はメモリ注入だけでなく、TITLEから実入力でStage 1 NORMALへ入った通常ゲームプレイ画面を最低1枚、Stage 1〜3のnormal/boss実行経路を各1枚以上、headless/GUI双方で保存する。各PNGについて実際のGameState/type/appearance/readbackとpixel照合を記録し、preview PNGと明確に分離する。
