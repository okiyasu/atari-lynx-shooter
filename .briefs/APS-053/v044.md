## 重要な訂正: tick換算則(実装前に必ず反映すること)

v042のディスアセンブル調査は「1 tick = 1 CPUサイクル」という誤った前提を置いていた。Fable5の算術検証により、実際は**Lynxのバス仕様上 1 tick ≈ システムクロック相当で公称CPUサイクルの約4.4〜5.0倍**であることが判明した(`evidence/APS-053/tick-calibration-v024.json`の「1 VBlank = 184,668 total_ticks」という既存較正値と、4MHz 65C02の物理制約から算術的に導出)。これにより「実測9,423tickの77〜85%が未解明」というv042の結論は誤りで、**机上見積りとほぼ一致することが確認された**(残差は解消済み、追加のディスアセンブル調査は不要)。

**この訂正はVBlank単位の既存報告(gate(a)=33 VBlank、(i)純Suzy=0.093 VBlank、(ii)SCB構築=1.98 VBlank等)には影響しない**(これらはtick-calibrationのVBlank較正値で算出済みのため正しい)。影響するのはCPUサイクル単位への換算のみ。

## 具体的な設計

### チェーン構成(描画順は現行と完全一致)

```
[envパレットヘッダ 19B] → env[0..3] 11B×4
→ [player 19B] → [enemyパレットヘッダ 19B] → enemy[0..7] 11B×8
→ [boss 19B] → [powerItem 19B]
→ [pbulletパレットヘッダ 19B] → pbullet[0..11] 11B×12
→ [ebulletパレットヘッダ 19B] → ebullet[0..15] 11B×16 → next=0
```

- 合計**573B**(現行529Bプール比+44B)。`next`で連結するため連続配置は不要。名前付きstatic構造体(`SCB_RENONE_PAL`/`SCB_RENONE`、cc65はパディングなし)として宣言し、リンクは初期化時に1回だけ張る
- スロット割当は**ゲーム配列の添字と1:1固定**(enemy[i] ↔ スロットi)。圧縮・詰め替えはしない。現行のkind内描画順(配列走査順)を保存する

### 非アクティブの扱い: SKIPビット採用(next張り替えは不採用)

- 非アクティブスロットは`sprctl1`にSKIPを立てるだけ(定数1バイトストア)
- next張り替え案は不採用(生死遷移ごとのポインタ簿記がCPU側バグ源になる、節約効果もSuzy側は既に0.093 VBlankで無視できる規模のため)

### REUSEPAL×SKIPの相互作用の解決(v039で指摘された懸念点)

「SKIPされたSCBがパレットをロードするか否か」というハード仕様の曖昧さに一切依存しない構造にする:

- **複数スロットkind(env/enemy/pbullet/ebullet)**: 先頭に**パレット専用ヘッダSCB**(19B、常にSKIPしない、data=1バイトの空スプライト)を常設。ゲームオブジェクトのスロットは全て11BのREUSEPALフォロワーになり、どれがSKIPされてもパレットは必ずヘッダが直前に供給する
- **単一スロットkind(player/boss/powerItem)**: フォロワーが存在せず相互作用が原理的に無いため、ヘッダを置かず自前penpal付き19B SCBのままSKIP可とする(3ヘッダ分57B節約)
- パレットヘッダの`sprctl0`は**そのkindと同じBPP**にすること(BPPがpenpalロードバイト数を決めるため)

### 初期化タイミング

| タイミング | 書く内容 |
|---|---|
| 起動時1回(TGI初期化後) | 全SCBの`sprctl0`(solid系定数)/`sprctl1`基底/`sprcoll=NO_COLLIDE`/`next`連結/ヘッダのdata=空スプライト/solid系kindの固定penpal(bullet・power・envの色)とdata(bullet/power形状) |
| ステージ開始時 | enemyパレットヘッダのpenpal・sprctl0(そのステージのkind代表defから。ステージ内でenemy/mineralの一方のみという既存検証済み不変条件に依拠) |
| ボス出現時(またはステージ開始時) | boss SCBのpenpal・sprctl0・dataキャッシュ |

### フレーム毎の差分更新

- 現行の`draw_environment`/`draw_game`のappend呼び出し部を、kindごとの**ポインタ歩行ループ**(`p++`方式、cc65は配列添字より速い)に置換。CADENCE_PROBEマーカー(`movable_scb_begin`/`movable_scb_finish`)の呼び出し位置は維持し、(ii)窓の比較可能性を保つこと
- **生死条件は現行append条件の逐語ミラー**とする: env=phase NORMALかつactive/FALLING、player=非dyingかつvisible、enemy=activeかつx<160、ebullet=activeかつy≥HUD、ALL_CLEARは全スロットSKIP、風ステージはenv全SKIP(TGI描画は現行のまま)
- アクティブ時の書き込み: `sprctl1`(SKIP無し定数)+`hpos`+`vpos`、アニメのあるkindのみ`data`。非アクティブ時: `sprctl1`(SKIP付き定数)のみ
- **sprite系(enemy/boss)のみスロットキャッシュ**を持つ: `{sprite_id, frame0_ptr, frame1_ptr, dx, dy}`(7B×9スロット=63B)。毎フレームはid比較1バイトのみ、typeが変わったときだけ`game_sprite_definitions`参照(=`mulax9`はスポーン時のみに退避)。anchorのdx/dyもキャッシュから加算。playerはid固定なので起動時に確定できる
- チェーンは**常時submit**(`tgi_sprite(静的ヘッダ先頭)`)。全SKIPフレームでもパレットヘッダ4個の空描画だけで、コストは無視できる
- プールオーバーフローガード(`main.c:510`)は構造上不要になり撤去
