## 問題: gate(d)(MAIN余剰≥512B)を大きく下回った

release/cadence両方でビルド・`make clean && ./scripts/verify.sh`(全PASS)を実行した後、gate(d)を再計測したところ:

| 構成 | 前回コミット時点(v046) | 今回(v048実装後) |
|---|---:|---:|
| release余剰 | 1,069B | **182B** |
| cadence余剰 | 947B | **46B** |

目標(≥512B)を大きく下回った。

原因を`static_layer.o`単体で切り分けたところ(コミット済みHEAD版と作業ツリー版でビルド比較、release):

| | HEAD(対策前) | v048(対策後) | 差分 |
|---|---:|---:|---:|
| CODE | 2,787B (0xAE3) | 3,563B (0xDEB) | **+776B** |
| RODATA | 68B (0x44) | 88B (0x58) | +20B(`hud_cell_byte_offset`テーブル、想定通り) |
| BSS | 4B | 30B (0x1E) | +26B(`hud_prev_text`21B+`hud_prev_valid`1B+`hud_prev_score`4B、想定通り) |

**CODEの+776Bが主犯**。RAM(BSS)側の見積もり(+26B)は正確だったが、コードサイズの見積もりを事前に行っておらず、v045/v046と同種の「C言語レベルでコード中立/削減を期待していたが実際は増加した」というパターンが3度目再発した。

## 該当コード(`src/static_layer.c`、現在の実装、未コミット)

```c
#define HUD_TEXT_LENGTH 20u
#define HUD_ROW_BYTES 16u

static const unsigned char hud_cell_byte_offset[HUD_TEXT_LENGTH] = {
    0u, 0u, 1u, 2u, 3u, 3u, 4u, 5u, 6u, 6u,
    7u, 8u, 9u, 9u, 10u, 11u, 12u, 12u, 13u, 14u
};

static char hud_prev_text[HUD_TEXT_LENGTH + 1u];
static unsigned char hud_prev_valid;
static unsigned long hud_prev_score;

static void hud_rebuild_skeleton(void)
{
    unsigned char row;
    unsigned char* p;

    p = HUD_DATA;
    for (row = 0u; row < STATIC_LAYER_FONT_HEIGHT; ++row) {
        unsigned char i;

        *p++ = (unsigned char)HUD_ROW_BYTES;
        for (i = 0u; i < HUD_ROW_BYTES - 1u; ++i) *p++ = 0u;
    }
    *p = 0u;
}

static void write_hud_cell_row(unsigned char row, unsigned char cell,
    unsigned char glyph_bits)
{
    unsigned char* dst = HUD_DATA + (unsigned int)row * HUD_ROW_BYTES + 1u +
        hud_cell_byte_offset[cell];

    switch (cell & 3u) {
    case 0u:
        dst[0] = (unsigned char)((dst[0] & 0x03u) |
            (unsigned char)(glyph_bits << 3));
        break;
    case 1u:
        dst[0] = (unsigned char)((dst[0] & 0xFCu) |
            (unsigned char)((glyph_bits >> 3) & 0x03u));
        dst[1] = (unsigned char)((dst[1] & 0x0Fu) |
            (unsigned char)((glyph_bits << 5) & 0xE0u));
        break;
    case 2u:
        dst[0] = (unsigned char)((dst[0] & 0xF0u) |
            (unsigned char)((glyph_bits >> 1) & 0x0Fu));
        dst[1] = (unsigned char)((dst[1] & 0x3Fu) |
            (unsigned char)((glyph_bits << 7) & 0x80u));
        break;
    default: /* 3u */
        dst[0] = (unsigned char)((dst[0] & 0xC0u) |
            (unsigned char)(glyph_bits << 1));
        break;
    }
}

static void write_hud_cell(unsigned char cell, char glyph)
{
    unsigned char row;
    unsigned char index;

    index = text_font_index(glyph);
    for (row = 0u; row < STATIC_LAYER_FONT_HEIGHT; ++row) {
        unsigned char bits = index < STATIC_LAYER_FONT_COUNT ?
            static_layer_font_bits[index * STATIC_LAYER_FONT_HEIGHT + row] :
            0u;
        write_hud_cell_row(row, cell, bits);
    }
}

static void append_hud(const GameState* game)
{
    char text[HUD_TEXT_LENGTH + 1u];
    unsigned char i;
    unsigned int timer_value;

    if (game->score != hud_prev_score) {
        unsigned long score_value = game->score;
        for (i = 5u; i != 0u; --i) {
            text[8u + i] = (char)('0' + score_value % 10ul);
            score_value /= 10ul;
        }
        hud_prev_score = game->score;
    } else {
        for (i = 9u; i <= 13u; ++i) text[i] = hud_prev_text[i];
    }
    /* ... timer/stage/phase/lives/weapon_level fields unchanged from
     * before ... */
    if (hud_prev_valid == 0u) {
        hud_rebuild_skeleton();
        for (i = 0u; i < HUD_TEXT_LENGTH; ++i) write_hud_cell(i, text[i]);
        hud_prev_valid = 1u;
    } else {
        for (i = 0u; i < HUD_TEXT_LENGTH; ++i) {
            if (text[i] != hud_prev_text[i]) write_hud_cell(i, text[i]);
        }
    }
    for (i = 0u; i <= HUD_TEXT_LENGTH; ++i) hud_prev_text[i] = text[i];
    /* ... append_scb(HUD_DATA, ...) unchanged ... */
}
```

## 気になる点(検証はしていない、参考まで)

- `write_hud_cell_row`のswitch文4パターンは、各パターンとも`dst`ポインタ計算(`HUD_DATA + row*16 + 1 + hud_cell_byte_offset[cell]`)を含む。cc65がこのポインタ演算をswitch文の各caseで重複生成している可能性がある(共通部分をcaseの前に一度だけ計算する形にできていない可能性)。
- `write_hud_cell`が7行ループの中で`write_hud_cell_row`を呼ぶ設計(関数呼び出しが1セルあたり7回)。v046の教訓(JSR/RTSオーバーヘッド)を踏まえると、インライン化や呼び出し構造の見直しで削減できる可能性がある。
- `hud_rebuild_skeleton`と`write_hud_cell`系のコード量が、想定より膨らんでいる可能性(cc65の構造体ポインタ演算・switch文コード生成の非効率、v045/v046と同種のパターン)。
