## 今回の依頼: Phase 3R着手前ゲート(実装ではなく検証・計算のみ)

**Suzy描画への実装(Phase 3R本体)には一切着手しないこと**。今回はデータ検証・実バイト数算出・収支表作成・到達可能性再計算のみ。

### 現状(T0/T1完了後の実測、今回の起点)

- MAIN余剰: release **2,356B**、cadence **1,912B**(`build/asteroid-patrol.map`/`build/asteroid-patrol-cadence.map`実測、STARTUP〜BSS連続範囲からの算出)
- ロジック理論下限: `evidence/APS-053/tick-calibration-v024.json`(4敵logic純増68 ticks、Timer2=105 ticks/VBlank、`logic_min_vblank=0.647619`)。Suzy描画下限は今回のゲートで確定させる

### 1. bpp変換方式の実装・検証

- `scripts/generate-stage-data.py` 側に4bpp/2bpp/1bpp変換を先行実装する(Makefileへの正式統合や既存ROMへの反映は不要。検証用に実行できればよい)
- bppはスプライトごとに実際の使用色数で最小化すること(全部を4bppにしない、という設計書の指示を守る)
- 対象は `assets/stages/stages.json` の `sprites`(13種)。各スプライトのフレーム数を実データから確認し、**26フレーム分**の実バイト数を確定させる

### 2. SCBフォーマット短縮設計の実バイト数試算

- スケール1x固定(APS-050)のため、SPRCTL1の再ロード指定を省略しHSIZE/VSIZEフィールド(4B)を削れる。パレット共有するスプライト間ではpenpal(8B)も省略できる。**フル23B/個ではなく11〜19B/個**を狙う(設計書記載の目安)
- 可動SCB置き場(約50個)の配置先候補を整理すること: BSS新設か、既存バッファ流用か。現状のscratch配置(`title_voice_scratch_buffer`640B、実効空き86B、SPACEテーマでSCB飽和)を踏まえ、新設が必要という前提で試算してよい(v2の記述と整合させる)

### 3. MAIN収支表の作成

- **追加**: (1)で算出したスプライトデータの実バイト数 + (2)のSCB置き場サイズ + 更新コード(データ比係数2で見積もる、v2 §2ルール2)
- **回収**: `sprite_data.o`(現状1,463B)+ `main.o` の可動描画コード該当分(`draw_sprite`/`draw_mask`/`draw_clipped_hline`/`draw_environment`/`draw_phase_overlay`等、実測すること)
- 上記の現状MAIN余剰(release 2,356B/cadence 1,912B)に対して、追加−回収を反映した後の余剰見込みを算出する

### 4. 到達可能性の再計算

- ロジック理論下限(`logic_min_vblank=0.647619`)に、今回確定させたSuzy描画データ量から見積もるSuzy転送・描画コストの下限を加算し、boss+敵4体+弾フルfixtureで**2 VBlank以下**に収まるかを判定する
- 収まらない場合、どの要素(ロジック/Suzy転送/SCB更新コード)が支配的かを内訳付きで報告すること
