## 発見した根本原因(実装前に必ず自分でも再確認すること)

`font_glyphs`(A-Z・0-9・`/`・`:`・`.`、7行×5列ビットマップ、各行は5bit値0〜31)を文字表示用データへ変換する箇所が、Python(`generate-static-layer.py` の `text_line_data()`)とC(`static_layer.c` の `build_text_line()`)で完全に同一ロジックになっている:

1. `compact = ((value >> 1) & 0x0f)` で5bit値を右に1シフトして4bitへ圧縮 → 元の最下位列(列4)が右シフトで欠落する
2. 描画ループが `for column in range(4): if column != 3 and (bits & (8 >> column)): ...` — `column == 3` のときだけ意図的に描画をスキップ → 4bit値の最下位ビット(元の列3)も描画されない
3. さらに元データ自体 `rows[:5]` で7行中上5行しか使っていない(下2行は未使用)

結果、実際に描画されるのは5列×7行フォントのうち左3列×上5行だけ。手計算でA/E/P/B/D/O/I/T等を再現したところ大半が酷似したパターンに潰れて判読不能になり、「2」だけ他と違う特徴的な形(下段空白+右下点)が残るため読み取れる、という実機報告と一致した。Gearlynxのreadbackテストがpixel mismatch=0でPASSしていたのは、比較先のgolden期待値自体がこの崩れた表示のまま登録されていたためで、文字として正しいかどうかは一度も検証されていなかった。

## 今回の依頼(ユーザー承認済み: 選択肢a)

### 1. データ構造変更 — 5列×7行のフルフォント表示への拡張

- `font_glyphs` の5bit値・7行をそのまま使い、圧縮(`>>1 & 0x0f`)と `column != 3` スキップを撤廃する
- 対象: `scripts/generate-static-layer.py`(`text_line_data()` 相当)、`src/static_layer.c`(`build_text_line()`)。両者は必ず同一ロジックを維持すること(前回の不整合と同じ轍を踏まない)
- 影響する定数・データ構造をすべて再計算すること:
  - `TEXT_DATA_SIZE`(現状56byte、行数5→7・1文字あたりpixel幅4→5への拡張に伴い再計算)
  - 各行のpixelバイト数(現状20文字×4bit=80bit=10byte/行)→ 20文字×5bit=100bit分の再設計(バイト境界の扱いを含む)
  - 各行先頭のヘッダバイト(現状固定値`11`、Suzy literal 1bppのライン総バイト数を表す値のはず。再計算した行バイト数に合わせて修正)
  - `STATIC_LAYER_FONT_HEIGHT`(現状5固定)を7へ
  - `pixel`カウンタのラップ処理、空白埋め(`for (; c < 20u; ++c) pixel = ...`)等の周辺ロジック
- Suzy literal 1bpp SCBのフォーマット制約(ライン先頭バイトの意味、stride、境界揃え)を仕様通りに満たしているか確認すること。不明点があれば推測で進めず報告すること
- `src/static_layer_data.c` / `.h` を再生成すること

### 2. テスト自体の欠陥修正

- 既存のTITLE/GAME OVER readback回帰テストのgolden期待値は、崩れた表示のまま登録されていた(=検証になっていなかった)。修正実装後、**全26文字(A-Z, 0-9, `/`, `:`, `.`)をGearlynxで実レンダリングした視覚証跡(PNG等)を新規に取得し、目視で正しい文字形状であることを確認してから** goldenを確定させること
- 目視確認の証跡(全26文字が判読できる画像)を最終報告に添付すること。「pixel mismatchが0だから正しい」という自己言及的な検証だけで済ませないこと

### 3. バージョン番号

- `include/version.h` の `GAME_VERSION_STRING` を現在の `0.53.6` から `0.53.7` 以上へ必ず上げること(コード変更の有無に関わらず、ROM生成のたびに上げるプロジェクトルール)
